# Тестовое задание: Визуализация данных движения (Data Light)

## Описание проекта
Данный проект представляет собой решение тестового задания на позицию Junior Physical AI / R&D Assistant. Основная задача — изучить сырые телеметрические данные (трекинг), записанные VR-устройством, и представить их в наглядном, легко интерпретируемом виде.

В качестве входных данных использовался лог-файл `tracking Data_20260505_165740.txt`, содержащий покадровую запись положения пользователя (Head, Hands) и параметры оборудования.

## Выбранный подход: Анализ временных рядов (2D-графики)
Для решения задачи я выбрал метод статистического отображения данных — построение независимых 2D-графиков движения шлема (Head Tracking) по каждой из осей (X, Y, Z) с течением времени. 

**Обоснование выбора:**
* **Отсутствие геометрических искажений:** В отличие от 3D-проекций, линейные графики позволяют точно оценить амплитуду движения без искажения перспективы на плоскости монитора.
* **Изолированный анализ:** Разделение на оси X (Вправо-Влево), Y (Вверх-Вниз) и Z (Вперед-Назад) позволяет легко выявлять паттерны движения пользователя и отслеживать высокочастотные аппаратные аномалии.
* **Надежность:** Метод работает напрямую с сырыми данными `pose`, не требуя допущений о калибровке камеры.

## Инструкция по запуску
Проект написан на базовом Python с использованием библиотеки для визуализации данных.

1. Установите зависимости проекта:
`pip install matplotlib`

2. Убедитесь, что исходный лог-файл `tracking Data_20260505_165740.txt` находится в корневой директории со скриптом.

3. Запустите скрипт:
`python main.py`

## Наблюдения, проблемы и их решения (R&D Аналитика)

При работе с предоставленным датасетом я столкнулся с рядом особенностей реальных сырых данных (Data Cleaning) и применил следующие инженерные решения:

### 1. Проблема локализации разделителей в логах
* **Симптом:** При попытке парсинга массива координат `pose` возникала структурная ошибка. В исходных JSON-логах десятичные дроби были разделены запятыми (например, `-0,085` вместо `-0.085`), из-за чего метод парсинга ломал структуру, разделяя целую и дробную части.
* **Решение:** Я написал кастомный обработчик внутри цикла чтения, который принудительно склеивает разорванные элементы строки через точку перед их конвертацией в формат `float`. Это позволило безопасно извлечь координаты.

### 2. Аппаратный шум инициализации (Outliers)
* **Симптом:** На первых этапах визуализации графики получались сильно сплющенными. Анализ числового ряда показал наличие резкого "выброса" координат (аномального скачка) в самом начале записи.
* **Решение:** Подобная аномалия характерна для старта VR-оборудования (момент первичной калибровки камер и IMU-сенсоров). Для чистоты эксперимента я применил фильтрацию, программно отсекая первые 50 фреймов нестабильного трекинга до момента стабилизации датчиков.

### 3. Ограничения AR-оверлея (Наложение на видео)
* Изначально я провел ресёрч в сторону наложения 3D-точек трекинга поверх исходного эгоцентричного видео. 
* От этого подхода было решено отказаться. Анализ показал, что для корректного совпадения виртуальных точек с объектами на видео требуется обязательное применение матрицы параметров камеры (`cameraIntrinsics`, присутствующей в логах) для правильной проекции 3D-сцены в 2D-плоскость камеры. Использование простой линейной проекции приводило к отрыву трекинга от объектов из-за искажений перспективы (FOV). Чистый аналитический подход с графиками оказался более точным и репрезентативным.

## Возможные улучшения
При дальнейшем развитии этого пайплайна можно реализовать:
* Синхронизацию графиков по оси времени не по номеру фрейма, а по реальным наносекундам, используя параметр `timeStampNs`.
* Применение скользящего среднего или фильтра Калмана для сглаживания микровибраций шлема.
